# CAGRA 构建加速报告（seekdb × AMD hipVS）

本报告记录 seekdb 比赛基线（V5，commit `634888d9b`）上 CAGRA 索引构建与查询路径的优化、
可复现实测方法，以及在 AMD Radeon GPU 上的同机配对测量结果。文中所有时间都是本机实测值，
不是从其他 GPU 推算的。

## 0. 结论

| 路径 | 变更 | 基线（同机） | 候选 | 加速 | 召回变化 |
| --- | --- | ---: | ---: | ---: | --- |
| SIFT250K（250K×128） | `niter` 100→40，`gd=128, igd=256` | 46.45 s | 24.98 s | **1.86x** | R@10 1.0000 → 0.99998 |
| 250K×256 | 同上 | 54.57 s | 29.96 s | **1.82x** | R@10 0.99971 → 0.99966 |
| 查询 | 复用 search params 与显存缓冲 | 143.0 QPS | 144.1 QPS | 1.01x | 不变（搜索参数未改） |

（构建时间均含首条查询，即从 `CREATE VECTOR INDEX` 到第一条 `ORDER BY ... APPROXIMATE` 返回。）

候选参数在两组“困难数据”压力测试上也守住了基线 −0.005 的召回门限：

| 压力集 | 基线 R@10 | 候选 R@10 | 差值 | 构建加速 |
| --- | ---: | ---: | ---: | ---: |
| 250K×128 均匀随机 | 0.99028 | 0.98877 | −0.0015 | 47.25 → 25.53 s（1.85x） |
| 250K×256 均匀随机 | 0.92549 | 0.92261 | −0.0029 | 52.04 → 29.37 s（1.77x） |

更激进的 `niter=20` 能到 2.5–2.6x，但在均匀随机集上召回下降 0.008（128 维）到 0.025（256 维），
超过 0.005 的门限，因此不作为默认值。详见 4.4。

## 1. 计时口径与约束

比赛计时从 `CREATE VECTOR INDEX ... lib=cuvs` 开始，到第一条查询完成：

1. 扫描表并在 CPU/GPU 间传输数据；
2. 在 GPU 上构建 CAGRA 图；
3. 将图与向量写入快照；
4. 首条查询重载快照并服务结果。

因此优化只做两件事：**让 GPU 建图本身更快**，以及**让同一份工作更少地做无用功**。
没有把任何建图/加载工作移出计时窗口，也没有跨轮复用图或缓存。

固定约束：FP32、L2、`type=hnsw, lib=cuvs, m=16, ef_construction=200, ef_search=64`。
`m/ef_construction/ef_search` 属于 HNSW 语义，本实现不改变其对外语义；CAGRA 内部参数由
bridge 根据向量维度选择。

## 2. 建图参数

CAGRA 的图质量由三个参数控制：

- `graph_degree`（gd）：最终出度，也是查询时的 fan-out；
- `intermediate_graph_degree`（igd）：NN-descent 细化阶段使用的中间度数；
- `nn_descent_niter`（niter）：NN-descent 迭代轮数。

基线固定为 `gd=128, igd=256, niter=100`，即“用 256 度图迭代 100 轮，再剪枝到 128 度”。
在 W7900D 上对 250K 规模扫描后得到两条结论：

1. **igd 决定召回，不能省。** 256 维上把 igd 降到 128（`128/128/70`）后 R@10 从 0.9997
   掉到 0.9568，且构建时间 32.7 s 并不比 `128/256/40` 的 31.7 s 更快——省掉中间图没有收益，
   只有召回损失。igd 提到 384/512 反而更差（见 4.5）。
2. **niter 决定时间，但下限受数据分布约束。** 结构化数据（SIFT、簇集）上 10–20 轮就收敛；
   均匀随机数据上 NN-descent 需要更多轮才能把长程边找全，`niter=40` 是同时满足
   “基线 −0.005” 与最大加速的拐点。

默认值因此统一为：

```c
/* 两个维度形状使用同一组参数；gd 必须保持 128，因为 ef_search=64 查询走同一张图 */
gd = 128; igd = 256; niter = 40;
```

同时保留环境变量覆盖，便于复现扫描（评测环境不会设置它们）：

```text
SEEKDB_CUVS_GRAPH_DEGREE
SEEKDB_CUVS_INTERMEDIATE_GRAPH_DEGREE
SEEKDB_CUVS_NN_DESCENT_NITER
SEEKDB_CUVS_SEARCH_ITOPK        (默认 512)
SEEKDB_CUVS_SEARCH_WIDTH        (默认 4)
SEEKDB_CUVS_SEARCH_MAX_QUERIES  (默认 0 = cuVS 自动)
```

## 3. 测量环境

- GPU：AMD Radeon Cloud 实例，`gfx1100`，48 GB 显存（与评测机 Radeon PRO W7900D 同架构）
- 主机：AMD EPYC 9334，128 线程，503 GB RAM，Ubuntu 24.04
- 软件：ROCm 7.2.4、hipVS（`/opt/hipvs`）、GCC 13.3、CMake 3.28.3、LLD 18
- seekdb：基线 V5，`RelWithDebInfo` + unity build + LLD，`-DOB_BUILD_CUVS=ON`
- 数据：
  - SIFT250K：真实 SIFT1M 的前 250K 条（250K×128），4096 条查询，暴力 L2 精确真值；
  - 250K×128 / 250K×256 合成簇集（2000 个簇心 + 高斯扰动）；
  - 250K×128 / 250K×256 均匀随机集（最坏情况压力测试）。
- `nq`：SIFT 为 4096，其余为 2048；真值为暴力 L2 top-100。
- 每组测量都从空目录启动全新 observer，`LOAD DATA` 后再计时，避免缓存和残留状态。

同一实例上不同轮次之间有 5%–15% 的波动（共享集群，load average 常年在 40–90），
因此报告中的加速比都来自**同一实例、同一时段**的测量，而不是跨天或跨机器比较。

## 4. 构建结果

### 4.1 真实 SIFT250K（250K×128）

| 配置 | 构建含首查 | R@10 | QPS@10 |
| --- | ---: | ---: | ---: |
| 基线 `128/256/100` | 46.45 s | 1.00000 | 143.0 |
| **默认 `128/256/40`** | **24.98 s** | **0.99998** | **144.1** |
| `128/256/20` | 18.95 s | 0.99998 | 133.5 |
| `128/256/15` | 16.07 s | 0.99995 | 136.1 |
| `128/256/10` | 14.64 s | 0.99990 | 136.2 |

SIFT 上 20 轮已经足够，但为了 Hidden 集的分布不确定性，默认取 40 轮，代价约 6 s。

### 4.2 250K×256（合成簇集）

| 配置 | 构建含首查 | R@10 | QPS@10 |
| --- | ---: | ---: | ---: |
| 基线 `128/256/100` | 54.57 s | 0.99971 | 122.7 |
| **默认 `128/256/40`** | **29.96 s** | **0.99966** | **132.2** |
| `128/256/20` | 23.13 s | 0.99980 | 108.2 |
| `128/256/10` | 19.07 s | 0.99971 | 110.7 |
| `128/128/70`（原候选默认） | 32.73 s | 0.95684 | 97.3 |

`128/128/70` 是必须放弃的方案：既没有更快，召回也掉了 0.043。

### 4.3 128 维合成簇集上的参数扫描

| 配置 | 构建 | R@10 |
| --- | ---: | ---: |
| 基线 `128/256/100` | 49.17 s | 0.99978 |
| `128/256/60` | 34.37 s | 0.99968 |
| `128/256/40` | 26.78 s | 0.99973 |
| `128/256/20` | 19.18–19.87 s（3 次） | 0.99966–0.99973 |
| `128/256/10` | 16.48 s | 0.99973 |
| `128/128/40` | 20.64 s | 0.99395 |

`128/128/40` 比基线低 0.0058，已经越过门限，进一步说明 igd 必须保持 256。

### 4.4 召回压力测试：均匀随机数据

均匀随机向量之间距离高度集中，是 CAGRA 最难的一类输入，也最接近“Hidden 集比 SIFT 更难”
的假设。用它来确定 `niter` 的安全下限。

250K×128：

| niter | 构建 | R@10 | 相对基线 |
| ---: | ---: | ---: | ---: |
| 100（基线） | 47.25 s | 0.99028 | — |
| 60 | 35.36 s | 0.99077 | +0.0005 |
| **40（默认）** | **25.53 s** | **0.98877** | **−0.0015** |
| 20 | 19.59 s | 0.98247 | −0.0078 |
| 10 | 15.14 s | 0.96211 | −0.0282 |

250K×256：

| 配置 | 构建 | R@10 | 相对基线 |
| --- | ---: | ---: | ---: |
| 100（基线） | 52.04 s | 0.92549 | — |
| **`128/256/40`（默认）** | **29.37 s** | **0.92261** | **−0.0029** |
| `128/256/30` | 24.99 s | 0.91533 | −0.0102 |
| `128/256/20` | 20.71 s | 0.90039 | −0.0251 |

结论：`niter=30` 已经掉出容差，40 是安全下限；再往下只适合“确定是 SIFT 类结构数据”的场景。

### 4.5 被否决的方案

| 方案 | 实测 | 结论 |
| --- | --- | --- |
| 128 维用 `gd=64, igd=64` | R@10 0.3443 | 否决 |
| 256 维用 `igd=128`（`128/128/70`） | R@10 0.9568（−0.043），32.7 s | 否决 |
| `igd=384, niter=20` | R@10 0.8974 | 否决 |
| `igd=512, niter=20` | R@10 0.8394，46.2 s | 否决 |
| `niter=20` | 均匀 256 维 −0.025 | 否决（余量不足） |
| `niter=30` | 均匀 256 维 −0.0102 | 否决 |
| `itopk=1024` | 查询 QPS 下降、构建无收益 | 否决 |

## 5. 查询路径

原 bridge 每次调用都会：

1. `cuvsCagraSearchParamsCreate/Destroy`；
2. 三次 `cuvsRMMAlloc/Free`（query、ids、dist）；
3. 两次同步 `cudaMemcpy`。

对 250K 图、单条查询而言，这些固定开销与 kernel 时间同量级。优化后把 search params 和
三块显存缓冲挂在 handle 上复用（`itopk` 只增不减，`topk` 变化时自动扩容），并用
`pthread_mutex` 保护，保持 ABI 与搜索语义完全不变。

同机配对结果：

| 数据 | 基线 QPS@10 | 候选 QPS@10 |
| --- | ---: | ---: |
| SIFT250K | 143.0 | 144.1 |
| 250K×256 | 122.7 | 132.2 |

256 维的提升来自固定开销占比更高；128 维在噪声范围内。两组都没有查询回退，
`itopk=512, width=4` 保持不变。

## 6. 快照路径

`ob_cuvs_serialize` 需要先把 cuVS 图写到一个临时文件，再拷入 seekdb 的快照流。原实现
无条件使用 `tmpfile()`（落在磁盘）。现在：

- 先检查 `/dev/shm` 可用空间，足够（按上界估算）时使用 RAM-backed 临时文件；
- 空间不足或写入失败时自动回退到磁盘 `tmpfile()`，行为与基线一致；
- 文件在本次序列化结束即关闭删除，**不跨构建、不跨轮复用**。

该改动只减少构建窗口内的 I/O 抖动，不改变快照格式（magic 仍为 `OBCUVS02`）。

## 7. 合规性

- 未使用预编译 seekdb；代码基于 V5 冻结 commit `634888d9b`。
- 未复用任何上一轮的 CAGRA 图、索引文件或缓存；临时文件生命周期限于单次构建。
- 未降低 Recall：所有测量组召回 ≥ 基线 − 0.005，且满足绝对门槛。
- 构建与查询使用同一条实现路径；首条查询仍然完整执行快照重载。
- `lib=vsag` CPU 路径未改动。
- 参数只按向量维度选择，没有针对隐藏数据集的名称/哈希/分布做硬编码。

## 8. 复现

```bash
# 1) 构建 bridge（与评测环境一致）
tools/hipvs_bridge/build.sh /work/bridge/libseekdb_cuvs_bridge.so

# 2) 构建 seekdb（评测命令）
./build.sh release -DOB_BUILD_CUVS=ON \
  -DCUVS_BRIDGE_LIB=/work/bridge/libseekdb_cuvs_bridge.so --make -j64

# 3) 复现参数扫描（环境变量只影响当前进程，评测不会设置）
SEEKDB_CUVS_GRAPH_DEGREE=128 SEEKDB_CUVS_INTERMEDIATE_GRAPH_DEGREE=256 \
SEEKDB_CUVS_NN_DESCENT_NITER=100 ./observer ...
```

构建日志会打印实际生效的参数，便于核对：

```text
[seekdb_cuvs] build n=250000 dim=128 gd=128 igd=256 niter=40
```

## 9. 风险与后续

1. **Hidden250K 若接近均匀随机 256 维**，默认参数相对基线的召回余量约 0.002；若同轮基线
   波动导致越界，可把 `niter` 提到 50–60（构建时间增加 20%–40%）。
2. 绝对时间随实例负载波动较大（本机同日波动 5%–15%），正式成绩以同轮冻结基线配对为准。
3. 不要在评测轮设置任何 `SEEKDB_CUVS_*` 环境变量；默认值就是提交值。
4. Radeon Cloud 实例为临时资源（就绪后 4 小时自动删除），测量结果需及时导出。
